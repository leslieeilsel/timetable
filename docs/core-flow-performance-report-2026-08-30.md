# 核心流程性能对比（2026-08-30）

分支：`codex/core-flow-performance`

## 测量方法

- 生产构建；隔离的 Laravel API 与 Vite Preview；Chromium 1440×900。
- 每轮创建全新浏览器并禁用浏览器缓存。
- 核心流程固定为：冷启动 `/login` → 输入排课员账号并登录 → 等待工作台摘要 → 进入课表 → 切换教师视图 → 打开教师选择器 → 搜索“陈伟”。
- 原始基线取稳定构建的 3 次中位数；最终结果取 5 次中位数。另用有界面 Chrome 完整复核一次。
- Chromium CPU 是所有浏览器子进程之和，因此峰值可能超过 100%。

## 保留的更改

1. **班级课表不再等待全部任课任务分页。** 班级网格所需数据到达后立即显示，360 条任课任务继续在后台加载；任务未完成前编辑能力保持禁用，并显示明确的加载状态，避免用不完整数据编辑。结果是班级课表就绪时间降低 34.7%，连同教师视图的合计等待降低 26.2%。
2. **拼音搜索按需加载。** 中文、工号、学科等普通搜索不再预先加载 `pinyin-pro`。选择器核心分包从 149.38 KiB gzip 降至 7.64 KiB gzip；141.68 KiB gzip 的拼音分包只在输入拉丁字母并提交搜索时加载。核心流程传输量降低 16.0%，JS 堆峰值降低 25.2%。有界面验收中又用 `wangjing` 成功找到“王静”，确认延迟加载没有破坏拼音搜索。

## 已撤销的实验

- 尝试把任课任务从 4 个分页请求改成一次 `per_page=500` 请求。请求页数确实从 4 降到 1，但同批次的完整流程从 1994.9 ms 变为 2113.3 ms（+5.9%），课表就绪从 390.7 ms 变为 436.2 ms（+11.6%），INP 从 80 ms 变为 88 ms。该更改已完整撤销。

## 未解决的瓶颈

- 登录请求仍需约 200–262 ms，主要是安全的密码哈希校验。没有为了基准分数降低哈希强度。
- 360 条任课任务仍分 4 页加载，最终中位耗时 129.2 ms；它已不再阻塞班级课表首屏，但教师视图和编辑状态仍需要这批数据。当前核心流程中没有长任务或明显卡顿；如果数据量继续增长，下一步应设计只返回当前视图所需字段的轻量端点，而不是简单放大分页。
- API + Preview RSS 受服务进程运行时长影响，浏览器 RSS 与 JS 堆是更可比的内存指标。
